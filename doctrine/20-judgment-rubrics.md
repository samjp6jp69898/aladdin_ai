# 判斷力外化 Rubric（20-judgment-rubrics）

> 這份檔案把「強模型靠直覺做的判斷」翻譯成可判定的規則。每條有正例（✅ 這樣做對）與反例（❌ 這樣做錯）。
> 規則沒覆蓋到的情況：選「可逆、留紀錄」的那條路，並把該情況記進 `40-maintenance-protocol.md` 定義的踩坑流程。

## 1. 何時該升級模型（haiku→sonnet→opus）

**判準**：滿足任一 → 升級：
(a) 依 `10-model-dispatch.md` 第 5 節的錯誤次數觸發；
(b) 任務需要「跨兩個以上系統的因果推理」（如：前端症狀 → gRPC 協議 → 後端 handler → DB 狀態）；
(c) 錯誤的代價會污染下游（分析錯 → 修復、審查、MR 全白做）；
(d) 兩個可信來源互相矛盾、需要裁定誰對（spec vs 程式碼、文件 vs 實測）。

- ✅ 正例：sonnet fixer 兩次都把測試改綠但 reviewer 都判 FAILED（diff 與 tracer 分析不對齊）。第三次不再派 sonnet 改，而是升 opus 重看 analysis-notes 是否本身有誤，並附上兩次失敗 diff 與 reviewer 意見全文。
- ❌ 反例：haiku 做「把 20 個檔案的 import 路徑批次替換」時漏改 3 個檔，於是升 opus 來做替換。錯——這是 prompt 沒給完整檔案清單的問題，不是能力問題；修 prompt（附明確清單與驗收 `grep -c` 條件）再派 haiku/sonnet 即可。**升級處理的是「判斷不足」，不是「指令不清」。**

## 2. 何時算真的完成（宣告 done 的門檻）

**判準**：三者缺一不可：
(a) 驗收條件逐條有**可貼出的證據**（測試輸出、exit code、read-back 內容、截圖）；
(b) 證據來自**重新執行**，不是「我改完了所以應該會過」；
(c) 由**沒參與實作的 fresh-context agent** 或指揮官本人核對過證據與驗收條件的對應。

- ✅ 正例：fixer 宣告完成時附上 `bun test <相關檔>` 的最後 10 行（含 pass 數與 exit 0）、commit hash、與「analysis-notes 修復策略第 N 點 → diff 第 M 行」的對應表。reviewer 重跑測試後才判 PASSED。
- ❌ 反例：「已修復 GetTipAuditList 回傳空列表的問題，修改了 rajah 的 model 定義並重新生成 code」——沒跑任何測試、沒驗生成檔差異、沒確認 agrabah 端編譯。這不是完成，是「改了」。**「改了」≠「完成」；中間差一整個驗證。**
- 特別條款（本專案史實）：涉及**跨 repo 的修復**（rajah+agrabah+abu），完成定義必含「所有相關 repo 的節點都已列出且互相對應」——2026-06-01 就是 agrabah pick 了、rajah 漏 pick，正式環境才炸。

## 3. 何時該停下來問使用者（或走 needs_qa 給 QA）

**判準**：滿足任一 → 停下來問，不要自己裁定：
(a) **規格自相矛盾**且兩種讀法都能自圓其說（本 pipeline 的頭號實際卡點，佔 grounding 的 ~10%）；
(b) 需要**業務取捨**而非技術判斷（「應該顯示 0 還是顯示上期值」「by-design 還是 bug」）；
(c) 動作**不可逆且出界**（推 force push 到非 mr/FAQ-* 分支、刪除非本流程建立的檔案、動 production）；
(d) 發現的事實與使用者的前提矛盾（使用者說 A 壞了，實測 A 是好的——先回報，不要「順手修成你以為的樣子」）。

- ✅ 正例：FAQ-3075——spec 同時寫「未審批顯示 0」與「預估佣金不論是否送出都取值」，兩規則對同 4 個欄位給出不同答案。正確動作：走 needs_qa_clarification，把兩條規則原文、衝突點、兩種解讀各自的影響寫成**二選一的問題**給 QA。
- ❌ 反例：同樣情境下，模型自行選了「比較合理」的讀法直接改 code 發 MR。就算猜對了，這也是錯的流程——業務裁定權不在 AI；猜錯則浪費 reviewer 時間並可能上線錯誤行為。
- **問的品質門檻**：問題必須是「可直接回答」的形式——附證據、附選項、附各選項的後果。「請問這個需求怎麼做？」是爛問題；「規則 A 與 B 衝突（原文引用），選 A 則 X 欄顯示 0，選 B 則顯示上期值，請裁定」是好問題。

## 4. 什麼訊號代表方向錯了（該換路，而非再試一次）

**判準**：出現任一訊號 → 停止目前路線，回上一個分岔點：
(a) **同一手段連續兩次產生同一類失敗**（第三次不會不一樣）；
(b) 為了讓方案成立，需要的「例外」越來越多（改 A 要先繞 B、繞 B 要再補 C）；
(c) 新證據與該路線的**前提**矛盾（不是與細節矛盾）；
(d) 修復範圍不斷擴大（原判 1 檔，實作時變 5 檔還在長）——大概率 root cause 定位錯了層。

- ✅ 正例：worktree 內 `bun run migrate ControlCenter` 一直 ECONNREFUSED。兩次重試同錯後，換路：在**主 repo** 跑同指令 → 同錯 → 證明是本機環境既有問題，與 worktree 無關 → 標注 BOOTSTRAP_PARTIAL 續行，不再於 worktree 側「修」。（這條已固化進 setup-worktree.sh。）
- ❌ 反例：lint OOM（exit 137）後，把 lint 範圍縮小到只掃改動檔讓它「過」。這不是換路，是把驗證弄瞎。正路是加 `NODE_OPTIONS=--max-old-space-size=8192`（OOM 是必然事件，見 refs/build-oom.md）。**「繞過檢查」永遠不是合法的換路。**
- 換路的紀律：換路前寫下一行「原路線、失敗證據、新路線」（進 analysis-notes 或對話），否則下一個 session 會把你走過的死路再走一遍。

## 5. 品質底線怎麼驗（最低驗證組合）

按產出類型的**最低**驗證（可加碼不可減）：

| 產出 | 底線驗證 | 誰來驗 |
|---|---|---|
| 程式碼修復 | 相關單元測試綠 + lint 乾淨（帶 NODE_OPTIONS）+ diff 與分析對齊 | solution-reviewer（fresh context） |
| 新腳本 | `bash -n` + 至少一次真實輸入的實跑 + 失敗路徑至少測一條（給爛參數） | 寫的人跑，另一人 read-back 契約 |
| 文件/制度檔 | read-back：檔案存在、必要 section 齊、與宣稱一致；引用的路徑逐一 `ls` 驗證 | fresh-context agent |
| root cause 分析 | 每個結論有 file:line；call-graph 證據齊；五角度枚舉各有「適用+證據」或「不適用+理由」 | tracer 自查 + reviewer 對照 |
| MR | 分支對、目標 dev、reviewer 掛對人、CI 綠 | mr-pusher 契約 + 人 |

- ✅ 正例：本制度的 setup-worktree.sh 上線前：`bash -n`、dry-run 全流程、兩條失敗路徑（爛 ticket id、爛 repo 名）實測、發現多位元組解析 bug 並修掉。
- ❌ 反例：「腳本我看過一遍，邏輯沒問題」→ 上線 → `$TICKET）` 在 bash 3.2 炸出 unbound variable。**看過 ≠ 跑過。這個反例就發生在寫這份文件的當天。**

## 6. 誠實條款：rubric 補不了的事（harness 的極限）

以下情況**沒有**機械判準，弱模型不要假裝有：

1. **業務品味與取捨**（UI 文案語氣、「這修法會不會太侵入」、風險偏好）——正確動作：提出 2–3 個選項與各自後果，交給使用者/QA 選。不要自己選了再找理由。
2. **開放式規格的補全**（spec 沒寫的邊角行為）——正確動作：找同模組的既有行為做類比（附 file:line），依既有慣例補；找不到類比 → 問。
3. **新穎 bug 類型的 root cause 直覺**（回測顯示分析錯誤率 13.5%，多為此類）——正確動作：承認不確定度：分析結論標注「信心：高/中/低 + 依據」；低信心時建議 reviewer 加驗一條獨立證據鏈，或升 opus 出第二意見比對。
4. **「使用者真正想要什麼」**——prompt 模糊時，第一步是複述你的理解讓使用者確認（一句話），而不是做完 500 行再發現會錯意。自主 pipeline 裡沒有使用者 → 依 tracker/ticket 的字面 + grounding 實證，出入走 needs_qa。

## 7. 快查表（貼給自己）

```
要升級嗎？   → 錯誤代價污染下游 / 跨系統推理 / 兩源矛盾 / 次數觸發 → 升
完成了嗎？   → 重新執行的證據 + 逐條對驗收 + 非本人核對 → 才算
該問人嗎？   → 規格矛盾 / 業務取捨 / 不可逆出界 / 與使用者前提矛盾 → 問（附選項與後果）
該換路嗎？   → 同錯×2 / 例外堆疊 / 前提被推翻 / 範圍失控 → 換（先寫下死路）
底線驗證？   → 查上表；繞過檢查永遠不是選項
沒有判準？   → 選可逆留紀錄的路 + 記踩坑
```
