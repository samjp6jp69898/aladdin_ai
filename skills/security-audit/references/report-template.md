以下为完整报告模板，生成报告时严格遵循此结构。用 `[...]` 标注的部分需根据实际审计结果填充。

## 一、审计方法论

本次审计采用基于大模型的多轮、多 Agent 并行白盒代码审计方法论：

| 轮次 | 目标函数 | 方法 | Agent 数量 | 核心产出 |
|------|---------|------|----------|--------|
| 第一轮 | max(覆盖面) | 模式匹配(Grep) | [N] 个并行 | 高风险区域地图 |
| 第二轮 | max(深度) | 数据流逐行追踪(Read) | [N] 个并行 | 确认漏洞 + 排除误报 |
| 第三轮 | max(关联度) | 跨模块交叉验证 | [N] 个并行 | 攻击链 + 业务逻辑漏洞 |

**分析模型**: Source（用户可控输入）→ Propagation（数据传播/过滤）→ Sink（危险操作）

**优先级公式**: 优先级 =（攻击面大小 × 潜在影响）/ 利用复杂度

**轮次终止条件**（每轮结束后回答三个问题）：
- Q1: 有没有未覆盖的区域？→ 最终 NO
- Q2: 发现的入口点是否都追踪到了 Sink？→ 最终 YES
- Q3: 高风险发现之间是否存在跨模块关联？→ 已全部验证

## Formatting Rules

1. **Code blocks**: Always include file path and line number as comment on first line
2. **Data flows**: Use `↓` arrows and indentation, not bullet points
3. **Attack chains**: Use `├─` and `└─` tree notation with vulnerability cross-references like `[C-XX]`
4. **Tables**: Use `|---|` separator rows, keep columns aligned
5. **Vulnerability IDs**: Sequential within severity level: C-01, C-02, H-01, H-02, M-01, etc.
6. **Key lines in code**: Mark with `← [explanation]` comment
7. **CVSS scores**: One decimal place (e.g., 9.5, not 9 or 9.50)
8. **File references**: Use backtick-wrapped paths with line numbers: `path/to/file.ts:42`
9. **Severity tables**: Always include CVSS range column
10. **Fix estimates**: Use hours (h) for P0, can use days/weeks for P1+
